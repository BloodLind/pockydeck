# US-002 — Stable catalog and launch contract evidence

Recorded 7 September 2026 on branch `codex/f01-foundation`, based on planning baseline `ad2b66888841a3581b9685eec641d0d103717f2f` and the coordinator-accepted US-001 scaffold. This handoff does not accept US-002 or start US-003.

## Contract surface

Production domain contracts were added under:

- `core/domain/src/main/kotlin/dev/handheld/launcher/core/domain/model/`: stable IDs, item variants, availability/actions/categories/provenance, scoped inventory outcomes, launch acknowledgement and successful-open records.
- `core/domain/src/main/kotlin/dev/handheld/launcher/core/domain/repository/`: observable catalog, favorite, user-override and successful-open boundaries plus the launch dispatcher port.
- `core/domain/src/main/kotlin/dev/handheld/launcher/core/domain/policy/`: scoped reconciliation, acknowledged launch reduction and deterministic recent/title ordering.

The behavioral and failure-boundary reference is [contracts.md](../../contracts.md). Deterministic fakes exist only in domain test sources; no sample catalog or fake status ships in production.

## Acceptance evidence

### AC-01 — Stable component identity

Passed. `IdentityContractTest.twoActivitiesInOnePackageHaveDistinctStableLosslessIdentities` verifies that two fully qualified Activity classes in one package produce distinct `ItemId` values, survive lossless decode, retain identity after title change/rediscovery, and reject malformed encodings. `LaunchRequest` also rejects Android and external-content item/target mismatches.

### AC-02 — Non-destructive incomplete inventory and retained references

Passed. `InventoryPreservationContractTest` verifies:

- a nonempty partial payload with conflicting discovered fields and a new item changes only `InventoryStatus`; it cannot update, append, remove, or reorder cached records;
- a failed empty inventory preserves the same catalog;
- only a complete current-user Android inventory updates that scope;
- omitted Android records remain retained as `Unavailable(REMOVED)` while ROM and system-action records outside the scope remain unchanged;
- all unavailable reasons are excluded from `CatalogSnapshot.activeItems`;
- favorite IDs, successful-open records, category/artwork overrides and retained catalog records remain independent;
- cross-scope stable-ID collisions are rejected before a snapshot can be returned.

### AC-03 — Acknowledged successful open exactly once

Passed. `AcknowledgedLaunchPolicyTest` verifies one pending launch, suppression of repeated activation while pending, matching acknowledgement, no second effect from a repeated acknowledgement, and no successful-open candidate for failed dispatch or internal system actions. The in-memory contract repository returns `Recorded` once and `AlreadyRecorded` on the same operation ID.

The repository contract allocates the next globally serialized positive `openOrder` in the same local transaction as operation-ID deduplication and item upsert. A concurrent 40-operation fake test produced 40 distinct item records with the unique global orders 1–40.

External Android dispatch and the local persistence transaction are explicitly not described as cross-process atomic. A process death after dispatch but before recency commit must not replay the external intent and can leave that open absent from recency. Duplicate delivery to persistence remains locally idempotent.

### AC-04 — Deterministic recency and unopened order

Passed. `LibraryItemOrderingTest` verifies `[C, B, A] -> reopen B -> [B, C, A]`, one B entry, and unopened title/ID ordering. A separate malformed-history case verifies that a system action cannot become recent. The model contains no running-process state, playtime, duration, or wall-clock ordering authority.
