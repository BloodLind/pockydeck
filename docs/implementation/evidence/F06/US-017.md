## Transaction and preservation notes

`RoomCatalogRepository.applyInventory` enters one `RoomDatabase.withTransaction`
and delegates validation/reconciliation meaning to the accepted
`CatalogReconciliationPolicy`:

- valid incomplete results write only `inventory_status`; their observations do
  not touch catalog or reference tables;
- complete results upsert each discovered row and provenance with Room
  `@Upsert`, replace only that item's discovered action set, mark omitted
  in-scope rows `unavailable/removed`, and update status before commit;
- outside-scope ID collisions, duplicate IDs, out-of-scope payloads, mapper
  failures, or SQL failures abort the transaction;
- removal IDs are updated in chunks of 900 inside the same outer transaction,
  avoiding Android SQLite's common 999-binding limit without weakening
  atomicity; and
- reconciliation never deletes catalog rows or writes favorite, override, or
  history tables.

The snapshot Flow observes invalidation of catalog, provenance, action, and
status tables, then re-reads them inside a Room transaction and applies the
accepted `LibraryItemOrdering.titleThenId`. This avoids exposing a mixed catalog
generation. `CatalogSnapshot.activeItems` performs the accepted availability
filter while retained unavailable rows remain in `items` and `findItem`.

## Constructor handoff

The future `AppContainer` should create one application-owned database and share
that same instance across repositories:

```kotlin
val database = LauncherDatabase.open(applicationContext)
val catalogRepository = RoomCatalogRepository(database)
val favoriteRepository = RoomFavoriteRepository(database)
val itemOverrideRepository = RoomItemOverrideRepository(database)
```

`LauncherDatabase.open(context, databaseName)` defaults to
`handheld-launcher.db`, applies the explicit `LauncherMigrations.all` registry,
and never calls destructive fallback. Version 1 has no prior version to migrate,
so the registry is empty. The `MigrationTestHelper` check proves the exported v1
schema is available and opens; it does not claim a fabricated v1-to-v2 migration.
Future schema changes append reviewed migrations at the F06/coordinator
checkpoint. Do not create separate database instances for these repositories or
enable speculative multi-instance/cross-process invalidation. Opening Room must
not make discovery a startup prerequisite; cached observation remains available
independently of scan scheduling.
