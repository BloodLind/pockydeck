# US-022 safe Android component dispatch evidence

- Baseline: `bc60032` plus accepted US-020 and US-021
- Device verification: `emulator-5556`, Android 13 / API 33

## Public consumer boundary

`AndroidComponentLaunchDispatcher(context, dispatcher)` implements the accepted domain
`LaunchDispatcher`. It accepts only `LaunchTarget.AndroidComponent`, rejects the launcher's own
package, re-queries current-user `ACTION_MAIN` plus `CATEGORY_LAUNCHER` activities immediately before
dispatch, and requires an exact package/class match whose activity and application are enabled and
whose activity is exported.

After revalidation it starts the exact `ComponentName` with `ACTION_MAIN`, `CATEGORY_LAUNCHER`,
`FLAG_ACTIVITY_NEW_TASK`, and `FLAG_ACTIVITY_RESET_TASK_IF_NEEDED`. `Dispatched` is returned only
after `Context.startActivity` returns. A missing/disabled component, a race to
`ActivityNotFoundException`, a security rejection, and another runtime dispatch failure map to the
existing typed `TARGET_UNAVAILABLE`, `REJECTED`, and `DISPATCH_FAILED` reasons.

The adapter has no repository dependency and cannot write successful-open history. Its result is
only the existing `LaunchAcknowledgement`; it makes no process-liveness, suspension, or resume
claim. No production manifest entry or permission is required.

Android documents that application-context activity starts need `FLAG_ACTIVITY_NEW_TASK`, and that
`NEW_TASK` resolves an existing matching task or starts a new one according to task affinity. The
launcher-root reset flag supplies normal launcher entry behavior:

- [Context activity launch contract](https://developer.android.com/reference/android/content/Context#startActivity(android.content.Intent))
- [Tasks and the back stack](https://developer.android.com/guide/components/activities/tasks-and-back-stack)
- [Intent activity flags](https://developer.android.com/reference/android/content/Intent#FLAG_ACTIVITY_NEW_TASK)

## Acceptance mapping

- AC-01: JVM fakes cover absent/disabled, validation security rejection, launch security rejection,
  raced disappearance, and unexpected dispatch failure. API-33 PackageManager verification covers a
  nonexistent package and an actually disabled/restored fixture component.
- AC-02: API-33 PackageManager revalidated and launched the exact exported Settings launcher alias;
  a recording context verified MAIN/LAUNCHER and both task flags.
- AC-03: the API-33 task dump observed separate caller and Settings task IDs, then observed Settings
  retained after returning the caller task to the foreground.
- AC-04: contract review confirms the adapter returns only `Dispatched` or `Failed`; the Room test
  proves dispatch does not mutate successful-open history.

## Coordinator-owned integration delta

Construct `AndroidComponentLaunchDispatcher(applicationContext)` in `AppContainer` and expose it as
the existing `LaunchDispatcher`. F08 owns the sole successful-open write after it receives
`LaunchAcknowledgement.Dispatched`. No domain, Room schema, storage-format, Activity, Gradle,
manifest, or permission delta is required.
